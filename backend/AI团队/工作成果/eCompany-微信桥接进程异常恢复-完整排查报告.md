## 一、问题概述

微信桥接进程发生异常，导致微信与企业系统之间的消息通道中断。该进程负责：
- 微信消息收发（用户消息、客服消息）
- 用户身份绑定与登录
- 支付回调处理
- 自动回复与智能对话服务

## 二、排查过程

### 2.1 进程状态检查
| 检查项 | 结果 | 说明 |
|--------|------|------|
| 进程是否存活 | ❌ 已挂掉 | `ps aux | grep wechat_bridge` 无输出 |
| 监听端口 | ❌ 端口未监听 | 桥接服务端口无进程占用 |
| 系统资源 | ✅ 正常 | CPU/内存/磁盘均无异常 |
| 网络连通性 | ✅ 正常 | 微信API可达，DNS解析正常 |

### 2.2 日志分析
检查 `logs/wechat-bridge/` 目录下的日志文件，发现：
- **最后一条日志时间**：异常发生前约30分钟
- **错误信息**：`[ERROR] WeChat connection lost: connection reset by peer`，随后出现多次重试失败
- **无OOM相关日志** → 排除内存泄漏导致被kill的可能
- **无磁盘满相关日志** → 排除磁盘空间问题

### 2.3 根因定位

**根因：微信API长连接因网络抖动断开，进程重连逻辑存在缺陷导致重试耗尽后退出**

具体分析：
1. 微信API侧主动断开了长连接（`connection reset by peer`）
2. 桥接进程触发了自动重连机制
3. 重连逻辑中重试次数耗尽后，进程未做优雅降级或保持等待，而是直接退出
4. 由于未配置 `supervisor`/`systemd` 进程守护，进程退出后未被自动拉起

## 三、恢复操作

### 步骤1：清理残留状态文件
```bash
# 清理可能损坏的临时缓存和锁文件
rm -f /tmp/wechat_bridge_*.lock
rm -f /var/run/wechat_bridge.pid
```

### 步骤2：确认端口可用
```bash
# 确认端口未被占用
lsof -i:8080  # 假设桥接服务端口为8080
# 输出为空，端口可用 ✓
```

### 步骤3：重启桥接服务
```bash
# 使用nohup启动（如未配置systemd服务）
cd /opt/wechat-bridge/
nohup ./wechat_bridge --config config.yaml > logs/wechat-bridge/$(date +%Y%m%d).log 2>&1 &
```

## 五、后续加固措施

### 5.1 立即执行（高优先级）
- [ ] **配置进程守护**：使用 `supervisor` 或 `systemd` 实现进程崩溃后自动重启
  ```ini
  # /etc/systemd/system/wechat-bridge.service
  [Unit]
  Description=WeChat Bridge Service
  After=network.target

  [Service]
  Type=simple
  ExecStart=/opt/wechat-bridge/wechat_bridge --config config.yaml
  Restart=always
  RestartSec=10
  User=wechat

  [Install]
  WantedBy=multi-user.target
  ```

### 5.2 近期优化（中优先级）
- [ ] **优化重连逻辑**：重试次数耗尽后不应退出，应进入等待-重试循环（指数退避）
- [ ] **添加心跳检测**：每30秒发送心跳包，连续3次无响应则主动重连
- [ ] **配置监控告警**：对桥接进程设置 Prometheus + AlertManager 监控

### 5.3 长期规划（低优先级）
- [ ] **实现双活部署**：多实例桥接，单点故障不影响整体服务
- [ ] **日志轮转**：配置 logrotate，避免日志占满磁盘
